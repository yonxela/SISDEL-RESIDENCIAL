# CLAUDE.md - SISDEL Comunities (garita.app)

Instrucciones para cualquier sesion de Claude Code en este repo, en cualquier PC.

## Que es
Control de acceso para condominios (garita.app): paneles master, admin, vecino, garita y auditor, con camara LPR.
Multi-empresa: el rol `master` ve todo; `admin`, `policia`, `vecino`, `auditor`, `supervisor` y `operador` solo su condominio.
El `auditor` lo crea el admin: lee todo su condominio (menos los codigos de acceso), no escribe nada y tiene reportes con exportacion CSV.
Privilegios por usuario (idea de MULTISYS): el admin de cada condominio decide que puede ver o usar cada usuario. Ver la seccion "Privilegios por usuario" abajo.
Reportes (admin.html, boton Reportes): ver la seccion "Reportes y salidas" abajo.
Sistema Financiero (finanzas.html): es OIKOS, traido de MULTISYS; desde 2026-11-09 se mantiene solo aqui. Ver la seccion "Sistema Financiero" abajo.
Principio del dueno (2026-11-12): toda la informacion vive en el servidor, nada se borra y todo cambio deja rastro. Ver "Datos: tamano, sello del servidor, bitacora y respaldo" abajo.
Rondas (rondin/): es SISDEL RONDIN con su mismo diseno. Ver la seccion "Rondas" abajo.
Estructura de datos y archivos: ver README.md.

## Infraestructura
- Front: Vercel sirve garita.app directo desde la rama `main` de GitHub. Cada push a `main` publica solo.
- Backend: Firebase, proyecto `sisdel-datacenter` (Firestore, Auth, Functions en us-central1, Hosting espejo en sisdel-datacenter.web.app). Plan Blaze con la cuenta de facturacion "Garita.app" y alerta de 5 USD al mes.
- La camara envia a garita.app/api/lpr; Vercel lo reenvia a la Cloud Function `anprWebhook` (ver vercel.json). `decide.js`: un pase de visita vale lo que vale su vecino (moroso sin gracia, desactivado o eliminado: no abre ni con pase), coincidencia parcial de placas desde 6 caracteres, una visita temporal vale desde su `visitDate`; la respuesta `Close` lleva la razon real. Clave secreta por condominio en `_privado/camaras/claves/{id}` (`keyHash`; `cd scripts && npm run camera-key -- --condo=<id> --target=prod --generate|--ver|--quitar`): si existe, el webhook exige `?key=` (o `X-Camera-Key`) y responde Close "Clave de cámara inválida" sin tocar el condominio (queda en `camera_logs_huerfanos`); si no existe, la camara entra como antes. Al fijarla hay que cambiar la URL de la camara en el mismo momento. `verifyAccessCode` solo confirma vecinos (60 intentos / 10 min por usuario): confirmar el codigo de un guardia o administrador equivaldria a poder entrar con el. En `garita.html` un pase QR vale solo su dia (o su rango) y una vez, y un marbete o codigo de un vecino `active:false` no abre; el guardia resuelve alertas de panico desde la garita (`canResolve: panico.resolver`).
- El sistema anterior (Supabase) ya no se usa; sus datos se importaron el 2026-11-05.
- Acceso: GitHub `yonxela` (dueno) y `SisdelNir` (colaborador con push). Firebase: yonxela es Owner; la cuenta del papa de Yonathan es Editor + Cloud Run Admin (publica todo, no cambia permisos ni facturacion). Vercel publica los commits de cualquier colaborador porque el repo es publico.

## Privilegios por usuario
- Modelo: cada rol trae privilegios por defecto (campo `roles` de cada clave en `privilegios.js`) y son EXACTAMENTE el acceso que el rol tenia antes de este modulo. `usuarios/{id}.privilegios` guarda solo las diferencias (`{ clave: true|false }`); sin el campo, el usuario conserva el acceso de su rol (por eso no hubo migracion de datos). `usuarios/{id}.cargo` es el puesto (texto libre). El rol `operador` no trae ninguno: es el personal a la medida.
- Catalogo unico: `privilegios.js` (UMD: navegador y Node), 150 claves `modulo.accion` en grupos: 31 PARAGUAS (raices con `roles` por defecto: los 26 de siempre mas `mensajes.recibir`, `vecino.historial`, `vecino.contactos`, `reportes.ver` y `vecino.ficha`) y 119 ACCIONES con `parent`. Una accion no existe sin su paraguas y, con el, viene activa salvo que el usuario la tenga en `false`; hereda los roles por defecto del paraguas y su `onlyRoles`. `requires` es una dependencia blanda (la pantalla de privilegios la arrastra al marcar y quita las dependientes al desmarcar; no se comprueba en las reglas). Cada clave dice `enforce: 'reglas'` (las reglas de Firestore o el servidor la hacen cumplir) o `'pantalla'` (solo oculta en pantalla), `sensitive` y su subgrupo (`sub`). `functions/src/privilegios.js` es una COPIA IDENTICA: al cambiar uno, `cp privilegios.js functions/src/privilegios.js` (la prueba falla si difieren). Tambien trae las paginas (`PAGES`, con su privilegio de entrada), `landing()` (a donde manda el login), 11 plantillas del sistema (`TEMPLATES`, una de ellas, `sys-fiscalizador`, con rol `vecino`: un vecino con reportes en solo lectura; `SISDEL.otherPanels` ofrece `vecino.html` a un vecino con otros paneles y `vecino.html` muestra esos botones; las guardadas antes de las acciones se amplian con `expandTemplate`) y el motor de paraguas (`has`, `effective`, `toOverrides`, `toggle`, `cascade`, `childrenOf`, `descendantsOf`, `ancestorsOf`, `templateKeys`). El operador solo trae por defecto `mensajes.recibir` (leia los mensajes como miembro) y ninguna pagina.
- Las reglas leen el mapa del documento del usuario (no el token). Las funciones `pXxx(c)` NO se escriben a mano: las genera `cd scripts && npm run reglas` (entre las marcas BEGIN/END de `firestore.rules`) a partir del catalogo; un paraguas es `can(c, clave, roles)` y una accion `pParaguas(c) && childOk(c, clave)` (vale si el usuario no la tiene en `false`). Las claves `enforce: 'pantalla'` no tienen funcion (salvo los paraguas que usan sus acciones). `scripts/test-privilegios.mjs` verifica que el bloque este al dia, que cada clave y rol coincidan con el catalogo y que las funciones se usen. Las reglas ya no preguntan por el rol para dar acceso (no volver a usar `isAdmin`, `isStaff`...: usar `pXxx`). Las operaciones de Finanzas y Rondas se separan en las reglas por tipo de movimiento, campos que cambian (`diff().affectedKeys()`) y operacion (ver las secciones de abajo).
- Anti-escalada (no aflojar sin pensarlo; cada punto tiene prueba en `test-emulator.mjs`): quien crea una cuenta conoce su codigo y entra con ella, asi que `usuarios.crear` solo registra vecinos (guardias: `guardias.crear`; auditor, supervisor, admin y operador exigen ademas `usuarios.privilegios`). Nadie cambia sus propios `privilegios` ni `role` (solo el master); cambiar `privilegios` o `role`, y crear, editar o eliminar `admin` u `operador`, exige `usuarios.privilegios`; solo un `admin` u `operador` puede tener `usuarios.privilegios` (`onlyRoles` en el catalogo, `validUser` en las reglas), por eso `manageable()` puede decidir por el rol. Un codigo nuevo solo apunta a un usuario que se crea en la misma escritura (salvo `usuarios.codigos`, con el rol real del usuario y, sobre admin/operador, solo con `usuarios.privilegios`); quien ve codigos (`usuarios.codigos`) no ve ni borra los de admin/operador sin `usuarios.privilegios` (el cliente filtra `role in [vecino, policia, auditor, supervisor]`); `usuarios.eliminar` solo borra visitas, vehiculos y expedientes de un usuario que deja de existir en la misma escritura (`ownerGone`); nadie se elimina a si mismo. `usuarios.privilegios` equivale a control total del condominio: solo a administradores de confianza. Ver codigos o crear cuentas de guardia permite entrar como esa persona: tambien es sensible.
- Un solo "Salir" para todo el sistema: el boton de salida de cada pagina (`admin.html`, `garita.html`, `auditor.html`, `vecino.html`, `master.html`) pasa por `SISDEL.bindExitButton(boton, "pagina.html")`: en el panel principal del usuario (`SISDEL.homePage()`) cierra la sesion ("Salir"); en cualquier otro panel dice "Regresar al panel principal" y lleva ahi sin cerrar la sesion. No volver a usar `SISDEL.logout()` directo en el boton de una pagina.
- Salir de un modulo: en OIKOS (`finanzas.html`, funcion `exitToHome`) y en RONDIN (`rondin/js/sisdel-api.js`), "Cerrar Sesión" / "Salir" pasa a "Regresar al panel principal" (lleva a `SISDEL.homePage()` sin cerrar la sesion; OIKOS espera a que se guarde todo) cuando el modulo NO es el panel principal del usuario; si lo es (contador en OIKOS, supervisor en RONDIN) se queda "Cerrar Sesión". Se hace sin tocar `finanzas/` ni `app.js`: se relabela el boton con un MutationObserver (los menus se repintan) y el clic se intercepta en fase de captura, antes de `logout()` de OIKOS (que borraria la sesion de SISDEL). La sesion vencida de RONDIN sigue cerrandose sola con `API.logout`.
- Copiar codigos: `SISDEL.copyButton(codigo)` devuelve el boton "Copiar" (valor escapado en `data-copy`) y un escuchador global del nucleo copia el valor de cualquier `[data-copy]` con aviso y cambia el propio boton (`flashCopied`: palomita verde 1,8 s y vuelve a lo de antes; cruz roja si no pudo copiar); `SISDEL.copyText(texto)` hace la copia (portapapeles del navegador o respaldo con un campo oculto). Lo usan la lista de usuarios y la ventana de edicion de master.html y admin.html (en admin solo donde el usuario ya ve el codigo).
- Datos escritos por usuarios de menor confianza (nombres, telefonos, mensajes, placas y asuntos de visitas, nombre y casa de una alerta de panico) se escapan siempre al pintarlos (`esc`), tambien en `garita.html`, `panico-alertas.js` (el enlace del mapa) y en `rondin/js/sisdel-api.js` antes de pasarselos a RONDIN (que pinta con innerHTML); los ids de la base no van dentro de `onclick` (atributos `data-*` y un escuchador). Las reglas tipan `alertas_panico` (nombre, casa y telefono texto; lat/lng numero o nulo). `camera_logs.reason` se guarda SIN escapar y se escapa al pintar.
- Paginas: `SISDEL.can('clave')` muestra u oculta botones; `SISDEL.requireAuth([], 'pagina.html')` vuelve a leer la ficha del usuario (privilegios, rol y estado vigentes) y lo manda a la pagina que le toque. El login (`functions/src/auth.js`) devuelve `session.privilegios` y el destino; un usuario sin ninguna pagina no entra. Lo que se oculta en pantalla tambien lo bloquean las reglas: no confiar solo en la pagina.
- RONDIN y OIKOS se mantienen solo en este repo (desde 2026-11-09 MULTISYS queda aparte: ya no se recopian de alla y se pueden editar `rondin/js/app.js`, `rondin/css/style.css`, `rondin/js/i18n.js` y `finanzas/`). `rondin/js/sisdel-api.js` decide la pantalla por privilegios (`rondas.gestionar` = administra, `rondas.patrullar` = guardia, `rondas.ver` = solo lectura) y manda a su pagina de inicio a quien no tiene acceso. Ver "Rondas" para los privilegios por accion.
- Un solo formulario de ingreso: el de `index.html`. Ningun modulo pide su propia clave. Las paginas sin sesion mandan al login (`requireAuth`); `rondin/` tambien: `guardAccess` en `rondin/js/sisdel-api.js` redirige a `index.html?next=rondin/` y, tras entrar, el login vuelve a RONDIN si el usuario puede abrirlo (`next` solo acepta paginas de `PAGES`). Salir de RONDIN va al login (`SISDEL.logout('../index.html')`). El master va a `master.html` y el vecino a `vecino.html`, donde esta su boton de panico. La pantalla de clave original de RONDIN (`App.renderLogin`) ya no se alcanza.
- UI: `admin.html` tiene el boton "Configuracion" (encabezado) con una vista propia de tres pestanas, como el modulo de MULTISYS: Usuarios (lista con filtro por rol y Agregar Usuario, la misma de siempre), Privilegios (usuarios a la izquierda, tarjetas por modulo a la derecha, Marcar todos / Limpiar, plantillas, cambios sin guardar resaltados, Guardar / Descartar) y Plantillas (las del sistema en solo lectura; crear, editar, duplicar y borrar las del condominio en `plantillas_privilegios`). Se abre con `admin.html#configuracion/usuarios|privilegios|plantillas`. El boton lo ve quien tenga algun `usuarios.*`; con solo `usuarios.ver` todo queda en solo lectura (sin `usuarios.privilegios` no ve ni edita las plantillas del condominio). El escudo de cada usuario y Agregar Usuario siguen en el panel de siempre y abren los mismos componentes. `privilegios-ui.js` ofrece `mountEditor` (en linea), `openEditor` (ventana), `mountPrivilegesTab` y `mountTemplatesTab`; `master.html` usa la ventana. Para agregar un privilegio: entrada en `privilegios.js` + copia en functions + funcion `pXxx` y su uso en las reglas + ocultar o mostrar en la pagina + prueba en `test-emulator.mjs` (seccion "Privilegios por usuario").
- Anti-escalada tambien en las acciones: `plantillas.gestionar` cuelga de `usuarios.privilegios` (y por tanto solo admin y operador); un paraguas apagado apaga todas sus acciones aunque se las pongan en `true`. Con `usuarios.privilegios` basta para ver las plantillas del condominio; para guardarlas o borrarlas hace falta ademas `plantillas.gestionar`. El mapa de privilegios admite hasta 300 claves (un operador estrecho guarda cerca de cien en `false`).
- Orden de publicacion: reglas y functions primero (son compatibles con el front viejo: los usuarios de siempre no notan nada), el front (push a main) despues. Con el front antes que las reglas, el modal de usuario nuevo avisa de falta de permisos al leer las plantillas. Para crear `operador` y usar privilegios hacen falta las tres cosas.

## Reportes y salidas
- Boton "Reportes" en `admin.html` (junto a Configuracion, vista propia: `#reportes` es el catalogo en acordeon, como el modulo de Reportes de MULTISYS (categorias cerradas, una abierta a la vez; `#reportes/<categoria>` la abre desplegada y `#reportes/<reporte>` abre ese reporte con "Volver al catalogo"; ids: `garita-resumen|garita-vecinos|garita-visitas|garita-horas|garita-placas|garita-denegadas|garita-casas|morosos-fecha`); el panel, Configuracion y Reportes son vistas exclusivas: `paintViews`). Todo el codigo vive en `reportes-ui.js` (`SisdelReportes.available()`, `catalogFor(can)` y `mount()`), que se carga despues de `privilegios-ui.js` y de `reportes-export.js`. Garita se calcula ahi con `camera_logs`, `visitas` y `salidas`; Morosos sale de los usuarios; Finanzas y Rondas son accesos directos: la contabilidad NO se recalcula fuera de OIKOS (las cifras son siempre las suyas). `finanzas.html#reportes/income|expense-cat|month-balance|morosos|pay-map|account-statement|resumen` abre ese reporte dentro de OIKOS (`openReportFromHash`, solo la primera vez; el privilegio lo siguen decidiendo `finanzas-bloqueo.js` y `finanzas.reportes_*`). Dentro de OIKOS, Reportes muestra la misma lista de siete (`#rep-catalog`, con el aspecto del acordeon abierto, en el mismo orden: una prueba lo exige) y el reporte elegido la reemplaza con "Volver a los reportes" (`selectReport` / `showReportCatalog`); el reporte financiero (`openReportModal`, `#rep-tab-resumen`) tambien esta en la lista y sigue en Contabilidad. "Ingresos, egresos y saldo por mes" (`month-balance`, privilegio `finanzas.reportes_resumen`, que por eso tambien abre la pantalla Reportes) trae una fila por mes del rango (tambien los meses en cero), el total de cada ano y el total general: ingresos = pagos, egresos = gastos, saldo = ingresos menos egresos del mes (los cargos y cuotas no cuentan); el calculo esta en `finanzas/sisdel-reportes.js` (UMD, prueba `test-finanzas-reportes.mjs`). Todo reporte de OIKOS tiene grafica de barras, Imprimir, PDF, Excel (.xlsx de verdad, con `buildXlsx` de `reportes-export.js`, que OIKOS carga como `../reportes-export.js`) y WhatsApp (`whatsappText`): en la pantalla Reportes son `printCurrentReport`, `downloadCurrentReportPDF`, `exportCurrentReportExcel` y `shareCurrentReportWhatsApp` (privilegio `finanzas.reportes_exportar`); la ventana del reporte financiero conserva `printReport`, `downloadReportPDF`, `exportReportExcel` y `shareReportWhatsApp` y suma `toggleSummaryChart`. Antes la pantalla llamaba `printReport` y `downloadReportPDF`, que la ventana volvia a definir (salia la ventana en cero): una prueba exige que OIKOS no repita nombres de funciones. Cada reporte declara `numericCols` (columnas de montos: a la derecha en el PDF y la impresion, numeros en el Excel) y `rowsMeta[i].kind = 'subtotal'` para las filas de total de un ano. Aparte de la caja, el reporte por mes y la ventana del reporte financiero muestran "Cuotas y cargos emitidos" (cargos del periodo) y "Por cobrar al cierre" (`periodSummary` y `monthBalance`: de cada vecino vigente, cuotas y cargos menos pagos hasta el cierre; quien pago de mas cuenta cero; sin la mora por dia; con todo lo registrado coincide con el total de Morosos). Un periodo sin pagos ni gastos muestra un aviso (`notice`, que tambien va al PDF, la impresion, el Excel y WhatsApp; `sisdelNoCashNotice`) y una tabla vacia dice por que (`emptyText`): La Perla se cargo solo con cargos y veia todo en cero. La ventana abre en el ultimo mes con movimientos hasta el mes actual (no en el mas adelantado). "Tabla general" (mapa de pagos por residente, `pay-map`, privilegio `finanzas.reportes_morosos`; `paymentMap` en `sisdel-reportes.js`): una fila por residente y una columna por cada ano anterior (los de mas de 6 anos atras juntos en "Antes de ...") y cada mes del ano en curso hasta hoy; rojo = debe y ya vencio, verde = pagado, amarillo = debe pero aun no vence (no es mora), gris = sin cuota. Los pagos cubren primero lo mas antiguo (el reparto del reporte de Morosos); el vencimiento es el de OIKOS (`sisdelPeriodDue`: con mora por dia, ultimo dia del mes mas el plazo; sin ella, dia de cobro + gracia). Orden: de mayor a menor "Total que debe" (`totalOf` = `sisdelOwedOf(r).total`, el mismo saldo con mora de Residentes), al final los que estan al dia; columnas finales Meses en mora, En mora desde, Cuotas vencidas, Por vencer (tambien cargos de meses que aun no llegan), Mora a hoy y Total que debe (las tres primeras de dinero suman el total, siempre: `sisdelPayMap` las cuadra con `sisdelOwedOf`). Un condominio cargado desde una cartera (cargos con `importedFrom`, `sisdelInitialLoadAt`): a sus residentes de la carga (alta hasta un dia despues) los meses anteriores a `feeFrom` sin cuota les salen pagados (verde, `paidBefore` / `assumed`), porque la cartera solo traia lo que se debe; a quien entro despues, gris. `cellStatus[fila][columna]` colorea la tabla, la impresion, el PDF y el Excel (estilos 4 a 6 de `reportes-export.js`); `compact` es la version corta para WhatsApp; la columna del residente queda fija al desplazarse. Arriba de la tabla, en grande, cuantos estan en mora, con cuota por vencer y al dia en cuotas, lo que deben (las tres cifras de abajo) y la leyenda de colores con un cuadrito de cada color (`highlights`, `legend` y `hint` del reporte, `#rep-highlights` pintado por `repHighlightsHtml`; las cifras grandes tambien van como indicadores al PDF, la impresion, Excel y WhatsApp: `exportModel` las pone primero y `kpisFromTotals: false` evita repetir los totales). Lo que debe un residente es lo mismo en todos los reportes, la Tabla general, Residentes y el tablero (pedido del usuario el 2026-11-16): `sisdelOwedOf(r)` = cuotas y cargos pendientes (cargos menos pagos del libro; los pagos cubren primero cuotas y cargos) + mora a hoy (la mora por dia `moraDaily` que falta pagar: lo que sobra de los pagos la cubre) = total (el saldo con mora de Residentes); `sisdelOwedTotals` suma a todos. Lo muestran Morosos (columnas Cuotas vencidas, Por vencer, Mora a hoy y Total que debe, tambien quien solo debe mora, por el total), la Tabla general, el Estado de cuenta general y el reporte por mes (cifras grandes), la ventana del reporte financiero ("Lo que deben hoy los residentes", aparte de "Por cobrar al cierre", que no trae la mora) y el aviso de morosos del tablero. Los nombres se escapan al pintarlos (tambien en Morosos).

## Busqueda inteligente
- Un solo modulo para todo el sistema: `sisdel-busqueda.js` (UMD, logica pura, `scripts/test-busqueda.mjs`). Reglas: no importan mayusculas, acentos ni la enie ("nunez" encuentra "Núñez"); se busca al escribir, y cada palabra escrita es el PRINCIPIO de alguna palabra del registro ("jua per" encuentra "Juan Pérez", en cualquier orden); todas las palabras deben coincidir (en cualquier campo); las cifras (casa, telefono, DPI) tambien coinciden dentro del dato desde 3 cifras; si nada coincide por el principio se afloja (la parte escrita en cualquier lugar, desde 3 letras); los resultados salen ordenados (primero los que empiezan con lo escrito en el primer campo, que es el nombre). API: `query`, `score` (0 = no coincide), `filter(items, texto, getFields, {limit})`, `highlight(texto, busqueda)` (HTML ya escapado con `<mark>`: lo que viene de la base nunca se vuelve HTML) y `fold`.
- Donde se usa: la lista de residentes de OIKOS (`residentSearchFields`: nombre, lote, fase, telefono, correo, propietario, NIT y DPI; `visibleResidents()` es lo que muestra la lista), las empresas del panel programador de OIKOS, los selectores de residente de "Registrar ingreso" y "Cargo a un residente" (`initResidentPicker`: un campo de busqueda sobre el `<select>`, que sigue guardando la eleccion; mientras se busca la lista queda abierta y SIN nada elegido), los usuarios de `admin.html` (lista y Configuracion) y las cuatro busquedas de `auditor.html` (usuarios, visitas, vehiculos y accesos; ahi solo filtran, sin reordenar) y las rutas del monitor de RONDIN. Una busqueda nueva: cargar el modulo y filtrar con `SisdelBusqueda.filter`, no con `includes`.
- Formulario del residente de OIKOS (`#modal-resident`): un 30 % mas grande (`zoom: 1.3` con `max-height: calc(92vh / 1.3)`, solo desde 640 px de ancho), con Anterior / Siguiente (recorren la lista tal como se ve, con su busqueda: `resNeighbors`), contador "Residente 3 de 719", un buscador propio (`resJumpSearch`: hasta 8 resultados al escribir, flechas y Enter, clic en uno abre ese vecino) y los botones "Guardar y siguiente" (o "Guardar y agregar otro" al crear: `resAfterSave`). ## Datos: tamano, sello del servidor, bitacora y respaldo
- Por que: La Perla (719 lotes) llenaba localStorage en menos de un ano y, lleno, OIKOS no guardaba ni abria. Medido con `scripts/seed-carga-grande.mjs` y `medir-carga-grande.mjs` (Chrome sin ventana, ver `scripts/chrome.mjs`); `cifras-oikos.mjs` compara todas las cifras de OIKOS entre dos versiones con los mismos datos.
- Donde viven los datos de OIKOS en el navegador (`finanzas-datos.js`): en la memoria de `finanzas.html` (`window.sisdelFinanzasStore`; el `Store` de OIKOS lee y escribe ahi con las mismas reglas de siempre: `stampList` es su `Store.set`). Los registros guardados NO se modifican nunca (quien lee recibe copias): los comparten la lista de OIKOS, el espejo de la nube y las fotos de deshacer. Sin esa memoria (OIKOS fuera de SISDEL) sigue el camino viejo de localStorage.
- Copia del equipo (IndexedDB, base `sisdel-finanzas-<condominio>`, anotada en `sisdel_fin_bases`): el espejo de los movimientos de la nube (bloques + cambios sueltos) y lo pendiente de subir. Se borra al cerrar sesion (`clearFinanceCache` en `sisdel-core.js`) salvo que quede algo pendiente; se rehace sola cada 30 dias o con `finanzas.html?recargar=1`. La copia NO es la base: todo vive en Firestore.
- Lo pendiente de subir (no perderlo es lo que mas importa): se anota al instante en localStorage (`sisdel_fin_sin_subir_<condominio>`, `pendingBackup`) y ademas en IndexedDB; al abrir se sube solo. Queda como pendiente EXACTAMENTE lo que hoy difiere de la nube (`syncPending` en cada escritura y en cada subida): si el usuario deshace un cambio que no habia subido, deja de estar pendiente (si no, al volver a abrir resucitaba). La marca `sisdel_fin_pendiente_*` se quita solo cuando no queda nada pendiente, y las fallas se llevan por tipo (`failures`): una subida que sale bien no tapa otra que fue rechazada. Si el navegador no deja guardar nada, al salir se avisa que los cambios se pierden.
- Dos pestanas sobre la misma copia: cada carga completa empieza una "tanda" (`generation` en la informacion del espejo); una pestana cuya tanda ya no es la del espejo deja de escribirlo (asi nunca marca como completa una copia que otra dejo a medias) y sigue trabajando desde su memoria.
- Un registro que la nube tenia y que ya no esta en la lista de OIKOS se acaba de quitar en este equipo (se deshizo su alta): `applyRemote` no lo vuelve a poner aunque llegue el sello de su alta; lo que sigue es su anulacion.
- Si SISDEL ofrece su memoria y `finanzas-datos.js` no cargo, OIKOS se detiene (no sigue en localStorage, donde lo registrado no subiria) y `finanzas.html` no lo muestra.
- Carga: la primera vez los movimientos bajan por paginas de 3000 (se puede retomar si se corta); despues solo se piden los que cambiaron. "Que cambio" lo dice el sello del servidor `server_at`, que `onFinanceMovement` pone a cada movimiento que se crea o cambia (`functions/src/finanzas/sello.js`); la tarea diaria repone los que falten o queden atrasados (`recalcCondo(..., { sweep: true })`). El sello nunca llega a OIKOS ni se sube; las reglas no dejan que un cliente lo cree ni lo cambie (`stampUntouched`), solo perderlo al reescribir el documento entero (el servidor lo repone).
- Deshacer deja rastro: al deshacer una anulacion, una eliminacion de residente o un finiquito, la nube recibe `deleted: false` + `restored_at` (o `status: 'active'`) y conserva el motivo y la fecha de la anulacion (`revivedFields` en `finanzas-sync.js`). Nunca se borran campos en la nube.
- Bitacora (`functions/src/bitacora/`): cinco disparadores (`auditUsers`, `auditVehicles`, `auditFinanceResidents`, `auditFinanceMovements`, `auditFinanceSettings`) anotan en `condominios/{c}/bitacora/{idDelEvento}` cada alta, cambio o eliminacion: quien (`actorType`/`actorId` del evento de Firestore, con nombre y rol si es un usuario del condominio; lo que hace el servidor queda como "Servidor"), cuando (`at`, hora del servidor), que documento y el valor de antes y de despues de cada campo. Lo eliminado queda completo; `anular` y `restaurar` son acciones propias; el sello no genera anotaciones; las fotos se anotan por su tamano. La escribe solo el servidor (`allow write: if false`); la leen el master, quien tiene `usuarios.privilegios` y quien tiene a la vez `usuarios.ver`, `vehiculos.ver` y `finanzas.ver` (todo lo que la bitacora anota). Una anotacion nunca se pierde por ser grande: los textos largos y los binarios se anotan por su principio, tamano y huella, de un mapa (privilegios) solo las claves que cambiaron, y si aun asi Firestore la rechaza se guarda lo minimo (`minimalEntry`) en vez de reintentar sin fin. De un condominio que se esta eliminando no se anota nada: `purgeCondominio` lo marca primero con `purging: true`. El id de usuario `master` esta reservado en las reglas (un usuario con ese id se confundiria con el Master). Consultar: `cd scripts && node ver-bitacora.mjs --condo=<id> [--target=prod] [--doc=<id>]`. Los codigos de acceso no se anotan. Todavia no hay pantalla para verla.
- Pendiente de comprobar al publicar: en el emulador el evento no trae la sesion real (llega `fake-auth-id@gmail.com`), asi que hay que hacer un cambio de prueba en produccion y ver con `ver-bitacora.mjs` que `actorId` trae el id del usuario (si llega otra cosa, ajustar `userIdOf` en `bitacora/entrada.js`).
- Respaldo de la base (activado el 2026-11-15 con el visto bueno del dueno): recuperacion a un momento de los ultimos 7 dias, proteccion contra borrado de la base, respaldo diario (14 dias) y semanal los domingos (14 semanas). Para recuperar se restaura en una base NUEVA y se copia lo necesario; nunca encima de la actual. Ver README "Proteccion de la base".
- Orden de publicacion de este cambio: (1) reglas y functions (compatibles con el front viejo: el front viejo ignora `server_at`); (2) el front (push a `main`). Con el front nuevo y las functions viejas no hay sellos: cada equipo trabaja con lo que bajo y no ve los cambios de otros hasta rehacer su copia, asi que no invertir el orden.
- Emulador: no entrega mas de ~10 000 documentos seguidos a un navegador y, si se le pide (el front viejo con un condominio grande), llena el disco con su registro; y deja de entregar disparadores si se escribe o borra mucho con ellos en pausa. `npm test` no los pausa nunca; `emulatorTriggersRespond` (scripts/admin.mjs) lo detecta y las pruebas piden reiniciar.
- Las reglas tampoco dejan que un cliente cree un movimiento con `serverGenerated: true` (esa marca evita el recalculo inmediato de la mora).
- Pruebas de este modulo: `test-finanzas-datos.mjs` (el Store de OIKOS en memoria contra el de localStorage, con miles de operaciones al azar), `test-finanzas-carreras.mjs` con `firestore-falso.mjs` (deshacer justo cuando llega el sello, crear y deshacer antes de subir, dos pestanas...: cada caso fallaba antes de su correccion), `test-finanzas-nube.mjs` (emuladores, varios equipos), `test-bitacora.mjs` y `test-finanzas-navegador.mjs` (Chrome). Al tocar `finanzas-sync.js` o `finanzas-datos.js`, correrlas todas.
- Pendientes anotados (no son de este cambio, salieron en la revision): la ventana de 2 horas para devolver una anulacion se mide con `updated_at`, que escribe el cliente, y un "toque" la renueva (quien tiene `finanzas.usar` y `finanzas.deshacer` puede devolver una anulacion vieja; ahora queda en la bitacora); si el disparador que sella falla, los demas equipos no ven ese movimiento hasta la tarea de las 05:00; eliminar por la pantalla un condominio muy grande y viejo puede pasar de los 300 s de la funcion (usar `scripts/purgar-condominios.mjs`).
- Limites conocidos: las fotos de comprobantes viajan dentro del movimiento (cada una pesa como 300 pagos): si se adjuntan seguido, la carga y la memoria crecen mucho (pendiente: guardarlas aparte). Un movimiento borrado a mano en la base queda como fantasma en la copia de cada equipo hasta que se rehace: para corregir, anular.

## Rondas: SISDEL RONDIN (rondin/)
- Es el programa RONDIN con su mismo diseno y opciones: `rondin/index.html`, `rondin/css/style.css`, `rondin/js/app.js` e `i18n.js` nacieron como copias de `RONDIN/public` y desde 2026-11-09 se mantienen solo aqui (si se edita `app.js`, revisar que sus llamadas `/api/...` sigan existiendo en el adaptador). Es la excepcion a la regla de emojis e iconos SVG. Las pipas quedaron fuera; Rondin Air (drones) esta incluido.
- Privilegios de RONDIN por accion (`rondas.*`): `rondin/js/privilegios-rondin.js` (UMD, se prueba en `scripts/test-rondas-privilegios.mjs`) tiene la tabla de rutas `/api/...` y el privilegio que exige cada una (`route()` de `sisdel-api.js` devuelve 403 si falta; una prueba exige que TODA ruta registrada en el adaptador este en la tabla o en la lista de rutas abiertas), las pantallas del menu (`App.navigate` con lista blanca; las pantallas huerfanas nunca se abren), la hoja de estilos que oculta botones por `onclick` y los metodos de `App` envueltos. `startRealtime` abre cada escucha solo con el privilegio de lo que escucha, `dispatchDrone` exige `rondas.drones_operar`, el tablero (`dgData`) tolera lecturas sin permiso y el expediente del guardia (`rondas.guardias_expediente`) se corta en `userOut`. Las reglas separan rutas (crear, desactivar), puntos (agregar, quitar o renombrar se distinguen por el cambio en la cantidad de `checkpoints`), asignaciones, alertas, incidentes, drones, configuracion, supervisor asignado y la patrulla (iniciar, marcar, terminar, rastrear); ver el mapa en vivo y el historial de ubicaciones son privilegios sensibles. El panel, los reportes, las listas de guardias y supervisores y el expediente son `enforce: 'pantalla'`.
- `rondin/js/sisdel-api.js` reemplaza al servidor de RONDIN (Express + SQLite en Render): define `API`, un `io()` sobre Firestore (tiempo real) y atiende los `fetch('/api/...')`. Responde las mismas rutas con los datos de SISDEL.
- Una sola base: empresa = condominio; guardias = `policia`, supervisores = `supervisor`, director general = `admin` (el `auditor` ve lo mismo en solo lectura; con privilegios a la medida, un `operador` puede ser cualquiera de ellos: ver "Privilegios por usuario"); el PIN de RONDIN es el codigo de acceso de SISDEL. Vecinos = los de SISDEL: DPI en `finanzas_residentes.dpi` (el del Sistema Financiero), familiares en `emergencia/{userId}`. Un vecino creado en RONDIN entra al Sistema Financiero desde ese mes (`feeFrom`).
- Datos propios con el formato de RONDIN (`company_id`, `guard_id`, fechas `AAAA-MM-DD HH:MM:SS` en UTC): `rondas_rutas` (con sus puntos), `rondas_asignaciones`, `rondas_turnos`, `rondas_rondas`, `rondas_visitas`, `rondas_ubicaciones`, `rondas_en_vivo`, `rondas_incidentes`, `rondas_alertas` (panel de alertas), `rondas_fotos`, `rondas_personal` (expediente del guardia), `rondas_config/general`, `rondas_drones`.
- El supervisor registra guardias (solo `policia`) y ve sus codigos; no ve los de los demas. `rondas.html` y `rondin.html` solo redirigen a `rondin/`.
- Boton de panico: guardias (RONDIN) y vecinos (RONDIN o vecino.html) crean `alertas_panico`. En vecino.html el boton aparece solo si RONDIN > Configuracion > "Vecinos usaran boton de panico" esta activo. `panico-alertas.js` (con `rondas-core.js`, que quedo solo para panico y contactos) los muestra en garita y admin; RONDIN tiene su propia alarma. `onPanicCreated` avisa por WhatsApp a la central, al admin y supervisores y a los familiares del vecino (hasta 5).
- WhatsApp: UltraMsg (principal) y Meta (respaldo), claves en `_privado/whatsapp`. Las carga una persona con `cd scripts && GOOGLE_CLOUD_QUOTA_PROJECT=sisdel-datacenter node set-whatsapp.mjs --target=prod` (sin claves, la alerta queda registrada como "WhatsApp sin configurar"). Con `--probar` verifica las claves con el proveedor sin enviar mensajes; con `--ver` muestra que esta configurado. En el emulador el proveedor es "simulado".
- `dailyRondas` (03:00 de Guatemala) cierra turnos de mas de 16 h y rondas de mas de 6 h (con su puntaje: % de puntos obligatorios, completa desde 80 %, igual que RONDIN) y borra posiciones de mas de 30 dias y alertas del panel de mas de 90.

## Requisitos en una PC nueva
- `node` 22 o mas, `firebase-tools`, `gcloud`, `gh` y Java 21 o mas (lo piden los emuladores).
- En Mac con Homebrew: `brew install node gh firebase-cli openjdk@21` y `brew install --cask gcloud-cli`. `openjdk@21` no queda en el PATH: agregar `$(brew --prefix openjdk@21)/bin` en `~/.zprofile`.
- En este repo, `git config user.email` con el correo noreply de GitHub (el repo es publico y el correo de cada commit queda visible).
- Entrar con una cuenta de Google con acceso al proyecto: `firebase login` y `gcloud auth login`. Para los scripts de `scripts/` tambien `gcloud auth application-default login`.
- `npm ci` dentro de `functions/` y dentro de `scripts/`.
- Si node se cuelga al importar firebase-admin, o el emulador dice "Timeout after 10000" al cargar functions: `rm -rf node_modules && npm ci` en esa carpeta.
- Puertos de emuladores: auth 9099, functions 5001, firestore 8080, hosting 5050, UI 4000.

## Herramientas y diagnostico
- `scripts/set-master-code.mjs --target=prod --generate` (con `GOOGLE_CLOUD_QUOTA_PROJECT=sisdel-datacenter`): genera un codigo master nuevo, guarda solo su hash en `_privado/auth`, cierra las sesiones master abiertas y muestra el codigo una sola vez. Lo corre una persona en su terminal: el modo automatico de Claude no deja escribir credenciales en produccion.
- `scripts/set-camera-key.mjs` (`npm run camera-key -- --condo=<id> --target=prod --generate`): clave secreta de la camara de un condominio (ver Infraestructura). Lo corre una persona; la clave se muestra una vez.
- Cambiar el nombre de un condominio (desde 2026-11-15, pedido del usuario): solo el programador, con la clave master. Boton "Cambiar nombre" en los detalles de cada condominio de master.html; el servidor (`renameCondominio`, `functions/src/condominios.js`) vuelve a verificar la clave aunque ya haya sesion master (5 claves incorrectas bloquean 15 minutos, bucket `renombrar`), limpia espacios (3 a 80 letras), guarda `previousName` y `renamedAt`, copia el nombre a `finanzas_config/oikos_settings.name` (queda en la bitacora) y deja `condominio renombrado` en el log. Las reglas no dejan cambiar `name`, `previousName` ni `renamedAt` desde el navegador (ni al master) y OIKOS solo puede guardar el nombre oficial (`officialName()`); en OIKOS el campo "Nombre del Residencial" es de solo lectura y `finanzas.html` abre con el nombre vigente (`SISDEL.getCondominio`). Los demas paneles muestran el nombre de la sesion hasta volver a entrar.
- Eliminar condominios por completo (lo mas grave que se puede hacer; no se deshace):
  - Un condominio: boton "Eliminar" junto a "Detalles" en cada condominio de la lista de master.html (y "Eliminar Condominio Definitivamente" en sus detalles). Abre una ventana que dice que se borra y pide escribir el nombre del condominio y la CLAVE MASTER de programador: aunque ya haya sesion master, el servidor (`deleteCondominio`, `functions/src/condominios.js`) vuelve a verificar la clave (`functions/src/master.js`, misma huella que el login) y el nombre (sin acentos ni mayusculas); 5 claves incorrectas bloquean el borrado 15 minutos (bucket `purga`). Mientras elimina, la ventana no se cierra y muestra los segundos que lleva (tarda hasta un minuto). Deja en el log `condominio eliminado` con el id, el nombre y los conteos (sin codigos).
  - Que se borra (`functions/src/purga.js`, `purgeCondominio`): el documento y todas sus subcolecciones, sus codigos de acceso (`codigos`), la clave de su camara (`_privado/camaras/claves/{id}`) y las cuentas de acceso (Firebase Auth) de sus usuarios; hace una segunda pasada tras unos segundos porque borrar movimientos del Sistema Financiero dispara el recalculo de mora (no recrea nada si el condominio ya no existe). Nunca toca `_privado/auth` (clave master), `_privado/whatsapp`, `mensajes_globales` ni la cuenta `master`.
  - Todos los condominios (limpieza total): `scripts/purgar-condominios.mjs` (`cd scripts && GOOGLE_CLOUD_QUOTA_PROJECT=sisdel-datacenter node purgar-condominios.mjs --target=prod`). Sin mas argumentos es un SIMULACRO (lista lo que borraria y lo que no se toca); `--respaldo` guarda un respaldo en `~/Desktop/RESPALDO SISDEL <fecha>` (JSON por condominio y `codigos.json`, permisos 600; se niega a guardarlo dentro de una carpeta de un repositorio: el repo es publico); `--eliminar --confirmo="ELIMINAR TODOS LOS CONDOMINIOS"` guarda el respaldo y borra (en produccion pide ademas escribir el numero de condominios, aunque no haya terminal; sin respuesta no borra; `--preguntar` lo hace tambien en el emulador, para las pruebas). `--excepto=id1,id2` conserva esos y `--solo=id1,id2` borra solo esos. Lo corre una persona en su terminal. Pruebas: `scripts/test-purga.mjs` y la seccion "Borrado de condominio" de `test-emulator.mjs`.
- `scripts/migrate-supabase.mjs`: importacion del sistema anterior (ya hecha).
- `cd scripts && npm run reglas` regenera las funciones `pXxx` de `firestore.rules` desde `privilegios.js` (`--check` solo verifica); `node scripts/generar-tabla-privilegios.mjs` regenera la tabla de privilegios del README (`--check` la verifica). Las dos las verifica `npm test`.
- Coleccion `_diag`: cada pagina guarda cuanto tardo en cargar (login, sesion, datos, red, navegador). Solo el master la lee; se consulta con el admin SDK desde `scripts/` para diagnosticar lentitud.
- Bitacora de logins en Cloud Logging: servicio `login`, campo `jsonPayload.outcome` (ok, not_found, blocked, condo_inactive, user_inactive).
