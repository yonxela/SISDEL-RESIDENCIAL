# CLAUDE.md - SISDEL Comunities (garita.app)

Instrucciones para cualquier sesion de Claude Code en este repo, en cualquier PC.

## Que es
Control de acceso para condominios (garita.app): paneles master, admin, vecino, garita y auditor, con camara LPR.
Multi-empresa: el rol `master` ve todo; `admin`, `policia`, `vecino`, `auditor`, `supervisor` y `operador` solo su condominio.
El `auditor` lo crea el admin: lee todo su condominio (menos los codigos de acceso), no escribe nada y tiene reportes con exportacion CSV.
Privilegios por usuario (idea de MULTISYS): el admin de cada condominio decide que puede ver o usar cada usuario. Ver la seccion "Privilegios por usuario" abajo.
Reportes (admin.html, boton Reportes): ver la seccion "Reportes y salidas" abajo.
Sistema Financiero (finanzas.html): es OIKOS, traido de MULTISYS; desde 2026-11-09 se mantiene solo aqui. Ver la seccion "Sistema Financiero" abajo.
Principio del dueno (2026-11-12): toda la informacion vive en el servidor, nada se borra y todo cambio deja rastro. Ver "Datos: tamano, sello del servidor, bitacora y respaldo" abajo.
Rondas (rondin/): es SISDEL RONDIN con su mismo diseno. Ver la seccion "Rondas" abajo.
Estructura de datos y archivos: ver README.md.

## Infraestructura
- Front: Vercel sirve garita.app directo desde la rama `main` de GitHub. Cada push a `main` publica solo.
- Backend: Firebase, proyecto `sisdel-datacenter` (Firestore, Auth, Functions en us-central1, Hosting espejo en sisdel-datacenter.web.app). Plan Blaze con la cuenta de facturacion "Garita.app" y alerta de 5 USD al mes.
- La camara envia a garita.app/api/lpr; Vercel lo reenvia a la Cloud Function `anprWebhook` (ver vercel.json). `decide.js`: un pase de visita vale lo que vale su vecino (moroso sin gracia, desactivado o eliminado: no abre ni con pase), coincidencia parcial de placas desde 6 caracteres, una visita temporal vale desde su `visitDate`; la respuesta `Close` lleva la razon real. Clave secreta por condominio en `_privado/camaras/claves/{id}` (`keyHash`; `cd scripts && npm run camera-key -- --condo=<id> --target=prod --generate|--ver|--quitar`): si existe, el webhook exige `?key=` (o `X-Camera-Key`) y responde Close "Clave de cámara inválida" sin tocar el condominio (queda en `camera_logs_huerfanos`); si no existe, la camara entra como antes. Al fijarla hay que cambiar la URL de la camara en el mismo momento. `verifyAccessCode` solo confirma vecinos (60 intentos / 10 min por usuario): confirmar el codigo de un guardia o administrador equivaldria a poder entrar con el. En `garita.html` un pase QR vale solo su dia (o su rango) y una vez, y un marbete o codigo de un vecino `active:false` no abre; el guardia resuelve alertas de panico desde la garita (`canResolve: panico.resolver`).
- El sistema anterior (Supabase) ya no se usa; sus datos se importaron el 2026-11-05.
- Acceso: GitHub `yonxela` (dueno) y `SisdelNir` (colaborador con push). Firebase: yonxela es Owner; la cuenta del papa de Yonathan es Editor + Cloud Run Admin (publica todo, no cambia permisos ni facturacion), salvo una funcion HTTP (`onRequest`) NUEVA: firebase-tools exige `cloudfunctions.functions.setIamPolicy` (Cloud Functions Admin u Owner) para crearla y se detiene antes de publicar nada; las callables y los cambios a funciones HTTP que ya existen si los publica. PENDIENTE (2026-11-17): `whatsappWebhook` (el aviso del chat de WhatsApp) todavia no existe en produccion; lo crea Yonathan desde main al dia con `firebase deploy --only functions:whatsappWebhook` (o le da Cloud Functions Admin a esa cuenta). ## Privilegios por usuario
- Modelo: cada rol trae privilegios por defecto (campo `roles` de cada clave en `privilegios.js`) y son EXACTAMENTE el acceso que el rol tenia antes de este modulo. `usuarios/{id}.privilegios` guarda solo las diferencias (`{ clave: true|false }`); sin el campo, el usuario conserva el acceso de su rol (por eso no hubo migracion de datos). `usuarios/{id}.cargo` es el puesto (texto libre). El rol `operador` no trae ninguno: es el personal a la medida.
- Catalogo unico: `privilegios.js` (UMD: navegador y Node), 160 claves `modulo.accion` en grupos: 33 PARAGUAS (raices con `roles` por defecto: los 26 de siempre mas `mensajes.recibir`, `vecino.historial`, `vecino.contactos`, `reportes.ver`, `vecino.ficha`, `finanzas.whatsapp_chat` y `panico.configurar`) y 127 ACCIONES con `parent`. Una accion no existe sin su paraguas y, con el, viene activa salvo que el usuario la tenga en `false`; la excepcion son las acciones `optIn` (hoy solo `finanzas.cuotas_meses`, "Cargar cuotas por mes", pedido del dueno el 2026-11-16): empiezan apagadas para todos, tambien para el administrador, y solo valen con `{ clave: true }` guardado en el usuario (`childOn` en las reglas, que el generador usa para ellas); no las encienden el paraguas, "Marcar todo", "Marcar todos" ni las plantillas (`bulkDescendantsOf`, `templateKeys`): se marcan a mano en Configuracion > Privilegios, usuario por usuario (al administrador se la marca el Master, porque nadie cambia sus propios privilegios), y la pantalla las marca "Se habilita aparte"; hereda los roles por defecto del paraguas y su `onlyRoles`. Otra excepcion, `autoRoles` (pedido del dueno el 2026-11-17: `finanzas.residentes_finiquitar` y `finanzas.residentes_eliminar`, las opciones "Finiquitar relacion" y "Eliminar" del menu de cada residente de OIKOS): la trae por defecto SOLO el rol de la lista (el administrador, que puede quitarsela con `{ clave: false }` y vuelve con su rol) y para cualquier otro rol empieza apagada AUNQUE tenga el paraguas `finanzas.usar`: solo vale con `{ clave: true }` guardado en el usuario (antes la recibia solo cualquier operador con "Usar el Sistema Financiero" o la plantilla Contador). No la encienden el paraguas, "Marcar todo" ni las plantillas de ese rol (`templateKeys(plantilla, rol)`, `expandTemplate(claves, rol)` y `toggle(..., { role })` miran el rol de quien recibe; sin rol, nunca): se marca a mano en Configuracion > Privilegios, usuario por usuario, y la pantalla la marca "Se habilita aparte" (`PRIV.explicitFor(clave, rol)`: true si para ese rol hay que marcarla, optIn o autoRoles; `isOptIn` sigue siendo solo la que empieza apagada para todos). En las reglas es `pParaguas(c) && childAuto(c, clave, ['admin'])` (el generador lo escribe solo; `childAuto` lee el mapa del usuario con el rol como valor por defecto). Quien ya tenia Finanzas por un rol que no es administrador (operador, auditor con paraguas...) pierde Finiquitar y Eliminar hasta que se le marquen; el administrador y el Master no notan nada. Las tres capas de OIKOS no cambian: reglas (`finanzas_residentes`), subida (`residentNeeds`) y pantalla (`finanzas-bloqueo.js`). `requires` es una dependencia blanda (la pantalla de privilegios la arrastra al marcar y quita las dependientes al desmarcar; no se comprueba en las reglas). Cada clave dice `enforce: 'reglas'` (las reglas de Firestore o el servidor la hacen cumplir) o `'pantalla'` (solo oculta en pantalla), `sensitive` y su subgrupo (`sub`). `functions/src/privilegios.js` es una COPIA IDENTICA: al cambiar uno, `cp privilegios.js functions/src/privilegios.js` (la prueba falla si difieren). Tambien trae las paginas (`PAGES`, con su privilegio de entrada), `landing()` (a donde manda el login), 11 plantillas del sistema (`TEMPLATES`, una de ellas, `sys-fiscalizador`, con rol `vecino`: un vecino con reportes en solo lectura; `SISDEL.otherPanels` ofrece `vecino.html` a un vecino con otros paneles y `vecino.html` muestra esos botones; las guardadas antes de las acciones se amplian con `expandTemplate`) y el motor de paraguas (`has`, `effective`, `toOverrides`, `toggle`, `cascade`, `childrenOf`, `descendantsOf`, `ancestorsOf`, `templateKeys`). El operador solo trae por defecto `mensajes.recibir` (leia los mensajes como miembro) y ninguna pagina.
- Privilegios de gerente (pedido del dueno el 2026-11-18: "unicamente los usuarios que tengan activados estos privilegios podran hacer lo que corresponde"): la PRIMERA tarjeta de Configuracion > Privilegios, "Privilegios de gerente" (grupo `gerente` con `handPicked: true` y una nota; borde ambar), junta lo que cambia lo que debe un residente o su historial: Residentes (`finanzas.residentes_eliminar`, `finanzas.residentes_finiquitar` y la nueva `usuarios.vecinos_nombre` "Cambiar el nombre de los residentes"), Saldos (la nueva `finanzas.saldos_modificar` "Modificar saldos de residentes", que ahora es el PARAGUAS de `finanzas.cargos_crear`, `finanzas.cargos_anular`, `finanzas.cuotas_meses` y `finanzas.cuotas_corregir`: sin ella ninguna vale; la Cuota del mes de todos y registrar pagos no la necesitan), Pagos y egresos (la nueva `finanzas.pagos_fecha` "Cambiar la fecha de un pago al registrarlo", `finanzas.pagos_anular` y `finanzas.egresos_anular`) Mora (`finanzas.mora_descontar` y `finanzas.reportes_descuentos`, el 2026-11-18: ver "Descontar mora"; cuelgan de `finanzas.usar`, no de "Modificar saldos", para que se den uno por uno) y Claves y usuarios (`usuarios.codigos` y `usuarios.eliminar`, que siguen siendo paraguas del administrador). Las acciones llevan `autoRoles: ['admin']` (las de cuotas por mes sigue `optIn`): el administrador las trae y se le pueden quitar; a cualquier otro rol hay que marcarselas una por una. `handPicked` hace que tampoco los paraguas de la tarjeta se enciendan en bloque para un rol que no los trae (`explicitFor`), y `PRIV.handOnly(clave, rol)` dice si algo se marca a mano o cuelga de algo que se marca a mano: no lo encienden el paraguas (`bulkDescendantsOf` ya no entra en lo que cuelga de una accion que se marca a mano), "Marcar todo" de las otras tarjetas, "Marcar todos" ni las plantillas (`templateKeys`); en una plantilla propia no se pueden marcar. El "Marcar todo" de la propia tarjeta de gerente si los marca (es marcarlos a mano). La tarjeta va primero en pantalla pero el motor la procesa al final (`ITEMS` pone los grupos `handPicked` al final: sus paraguas estan en otras tarjetas). Antes cualquier operador con "Usar el Sistema Financiero" (o la plantilla Contador, que ya no los trae) creaba cargos y anulaba pagos y egresos: ahora los pierde hasta que se le marquen; el administrador y el Master no notan nada. Donde se exige: (1) la fecha del pago: OIKOS tiene "Fecha del pago" en el Ingreso (`#inc-date-wrap`, `incomePayDate`, `checkIncomeDate`; hoy = la hora exacta, otro dia = ese dia a mediodia, nunca despues de hoy; el detalle del movimiento dice "Fecha del pago cambiada al registrarlo" con `txDateChanged`), `finanzas-bloqueo.js` la oculta sin el privilegio, `finanzas-sync.js` pide `pagos_fecha` si la fecha difiere mas de 10 minutos de `created_at` (`paymentDateMoved`) y las reglas (`incomeDateOk`) igual, ademas de que `created_at` no venga de mas de 7 dias atras ni de mas de un dia adelante (lo que un equipo tuvo pendiente de subir; asi no se cambia la fecha reescribiendo las dos desde la consola). (2) El nombre: reglas `vecinoNameOk` en `usuarios` (solo vecinos; al crear si se escribe), `residentNeeds` lo pide si cambia `name`, OIKOS deja `#res-name` de solo lectura al editar (el bloqueo envuelve `editResident` y `openModal`), la ficha de admin.html lo deshabilita y no lo manda (`nameLockedFor`) y RONDIN avisa antes de guardar (`PUT /api/neighbors/:id`). (3) Anular pagos y egresos: "deshacer" (`finanzas.deshacer`) ya no los anula, ni recien hechos: solo quita el alta de un cargo o una cuota (reglas y `movementNeeds`). LIMITE DE FIRESTORE: cada peticion evalua como maximo 1000 expresiones de reglas y, si se pasa, se RECHAZA (aunque deberia pasar). Con el nivel nuevo de "Modificar saldos", anular una cuota lo pasaba; por eso `childOk`, `childOn` y `childAuto` ya no repiten `isMember` (solo se usan como `pParaguas(c) && childX(...)`, que genera el script, y el paraguas raiz ya lo pregunta; una prueba lo exige) y la alternativa de deshacer mira primero el tipo y la ventana. Con eso las evaluaciones que pasaban el limite en `npm test` bajaron de unas 280 a cero. Revisado otra vez el 2026-11-22 (pedido del usuario): `npm test` deja unos 210 avisos en `firestore-debug.log`, TODOS de peticiones que DEBEN rechazarse y se rechazan (pasos como "guardia no edita usuarios", "cajero no anula pagos" o "config general: no cambia la cuota": al negar, Firestore evalua todas las alternativas y el emulador arma su explicacion del rechazo, y ahi se acaban las 1000); ninguna peticion permitida llega al limite (la prueba de OIKOS en Chrome y las de recordatorios, chat y purga dejan cero; si una permitida llegara, su prueba ademas fallaria). Por eso contar con grep ya no dice nada: al agregar niveles o condiciones a las reglas, correr `cd scripts && npm run seed && node --import ./limite-reglas.mjs test-emulator.mjs | grep -B1 LIMITE` (`scripts/limite-reglas.mjs` pone cada aviso debajo del paso que lo provoco) y revisar que ninguno caiga en un paso que debe pasar. Pruebas: seccion "Privilegios de gerente" de `test-privilegios.mjs`, `test-emulator.mjs` y `test-finanzas-navegador.mjs`, `test-finanzas-sync.mjs` y `test-finanzas-bloqueo.mjs`.
- Las reglas leen el mapa del documento del usuario (no el token). Las funciones `pXxx(c)` NO se escriben a mano: las genera `cd scripts && npm run reglas` (entre las marcas BEGIN/END de `firestore.rules`) a partir del catalogo; un paraguas es `can(c, clave, roles)` y una accion `pParaguas(c) && childOk(c, clave)` (vale si el usuario no la tiene en `false`). Las claves `enforce: 'pantalla'` no tienen funcion (salvo los paraguas que usan sus acciones). `scripts/test-privilegios.mjs` verifica que el bloque este al dia, que cada clave y rol coincidan con el catalogo y que las funciones se usen. Las reglas ya no preguntan por el rol para dar acceso (no volver a usar `isAdmin`, `isStaff`...: usar `pXxx`). Las operaciones de Finanzas y Rondas se separan en las reglas por tipo de movimiento, campos que cambian (`diff().affectedKeys()`) y operacion (ver las secciones de abajo).
- Anti-escalada (no aflojar sin pensarlo; cada punto tiene prueba en `test-emulator.mjs`): quien crea una cuenta conoce su codigo y entra con ella, asi que `usuarios.crear` solo registra vecinos (guardias: `guardias.crear`; auditor, supervisor, admin y operador exigen ademas `usuarios.privilegios`). Nadie cambia sus propios `privilegios` ni `role` (solo el master); cambiar `privilegios` o `role`, y crear, editar o eliminar `admin` u `operador`, exige `usuarios.privilegios`; solo un `admin` u `operador` puede tener `usuarios.privilegios` (`onlyRoles` en el catalogo, `validUser` en las reglas), por eso `manageable()` puede decidir por el rol. Un codigo nuevo solo apunta a un usuario que se crea en la misma escritura (salvo `usuarios.codigos`, con el rol real del usuario y, sobre admin/operador, solo con `usuarios.privilegios`); quien ve codigos (`usuarios.codigos`) no ve ni borra los de admin/operador sin `usuarios.privilegios` (el cliente filtra `role in [vecino, policia, auditor, supervisor]`); `usuarios.eliminar` solo borra visitas, vehiculos y expedientes de un usuario que deja de existir en la misma escritura (`ownerGone`); nadie se elimina a si mismo. `usuarios.privilegios` equivale a control total del condominio: solo a administradores de confianza. Ver codigos o crear cuentas de guardia permite entrar como esa persona: tambien es sensible.
- Un solo "Salir" para todo el sistema: el boton de salida de cada pagina (`admin.html`, `garita.html`, `auditor.html`, `vecino.html`, `master.html`) pasa por `SISDEL.bindExitButton(boton, "pagina.html")`: en el panel principal del usuario (`SISDEL.homePage()`) cierra la sesion ("Salir"); en cualquier otro panel dice "Regresar al panel principal" y lleva ahi sin cerrar la sesion. No volver a usar `SISDEL.logout()` directo en el boton de una pagina.
- Salir de un modulo: en OIKOS (`finanzas.html`, funcion `exitToHome`) y en RONDIN (`rondin/js/sisdel-api.js`), "Cerrar Sesión" / "Salir" pasa a "Regresar al panel principal" (lleva a `SISDEL.homePage()` sin cerrar la sesion; OIKOS espera a que se guarde todo) cuando el modulo NO es el panel principal del usuario; si lo es (contador en OIKOS, supervisor en RONDIN) se queda "Cerrar Sesión". Se hace sin tocar `finanzas/` ni `app.js`: se relabela el boton con un MutationObserver (los menus se repintan) y el clic se intercepta en fase de captura, antes de `logout()` de OIKOS (que borraria la sesion de SISDEL). La sesion vencida de RONDIN sigue cerrandose sola con `API.logout`.
- Copiar codigos: `SISDEL.copyButton(codigo)` devuelve el boton "Copiar" (valor escapado en `data-copy`) y un escuchador global del nucleo copia el valor de cualquier `[data-copy]` con aviso y cambia el propio boton (`flashCopied`: palomita verde 1,8 s y vuelve a lo de antes; cruz roja si no pudo copiar); `SISDEL.copyText(texto)` hace la copia (portapapeles del navegador o respaldo con un campo oculto). Lo usan la lista de usuarios y la ventana de edicion de master.html y admin.html (en admin solo donde el usuario ya ve el codigo).
- Datos escritos por usuarios de menor confianza (nombres, telefonos, mensajes, placas y asuntos de visitas, nombre y casa de una alerta de panico) se escapan siempre al pintarlos (`esc`), tambien en `garita.html`, `panico-alertas.js` (el enlace del mapa) y en `rondin/js/sisdel-api.js` antes de pasarselos a RONDIN (que pinta con innerHTML); los ids de la base no van dentro de `onclick` (atributos `data-*` y un escuchador). Las reglas tipan `alertas_panico` (nombre, casa y telefono texto; lat/lng numero o nulo). `camera_logs.reason` se guarda SIN escapar y se escapa al pintar.
- Paginas: `SISDEL.can('clave')` muestra u oculta botones; `SISDEL.requireAuth([], 'pagina.html')` vuelve a leer la ficha del usuario (privilegios, rol y estado vigentes) y lo manda a la pagina que le toque. El login (`functions/src/auth.js`) devuelve `session.privilegios` y el destino; un usuario sin ninguna pagina no entra. Lo que se oculta en pantalla tambien lo bloquean las reglas: no confiar solo en la pagina.
- RONDIN y OIKOS se mantienen solo en este repo (desde 2026-11-09 MULTISYS queda aparte: ya no se recopian de alla y se pueden editar `rondin/js/app.js`, `rondin/css/style.css`, `rondin/js/i18n.js` y `finanzas/`). `rondin/js/sisdel-api.js` decide la pantalla por privilegios (`rondas.gestionar` = administra, `rondas.patrullar` = guardia, `rondas.ver` = solo lectura) y manda a su pagina de inicio a quien no tiene acceso. Ver "Rondas" para los privilegios por accion.
- Un solo formulario de ingreso: el de `index.html`. Ningun modulo pide su propia clave. Las paginas sin sesion mandan al login (`requireAuth`); `rondin/` tambien: `guardAccess` en `rondin/js/sisdel-api.js` redirige a `index.html?next=rondin/` y, tras entrar, el login vuelve a RONDIN si el usuario puede abrirlo (`next` solo acepta paginas de `PAGES`). Salir de RONDIN va al login (`SISDEL.logout('../index.html')`). El master va a `master.html` y el vecino a `vecino.html`, donde esta su boton de panico. La pantalla de clave original de RONDIN (`App.renderLogin`) ya no se alcanza.
- UI: `admin.html` tiene el boton "Configuracion" (encabezado) con una vista propia de tres pestanas (mas "Boton de panico", ver la seccion de Rondas), como el modulo de MULTISYS: Usuarios (lista con filtro por rol y Agregar Usuario, la misma de siempre), Privilegios (usuarios a la izquierda, tarjetas por modulo a la derecha, Marcar todos / Limpiar, plantillas, cambios sin guardar resaltados, Guardar / Descartar) y Plantillas (las del sistema en solo lectura; crear, editar, duplicar y borrar las del condominio en `plantillas_privilegios`). Se abre con `admin.html#configuracion/usuarios|privilegios|plantillas`. El boton lo ve quien tenga algun `usuarios.*`; con solo `usuarios.ver` todo queda en solo lectura (sin `usuarios.privilegios` no ve ni edita las plantillas del condominio). El escudo de cada usuario y Agregar Usuario siguen en el panel de siempre y abren los mismos componentes. La busqueda de privilegios y la de usuarios de esa pantalla no importan acentos ni mayusculas y aceptan varias palabras (`matchesSearch`; pedido del usuario el 2026-11-22: escribio "panico" y no salia "QR de pánico"); la de privilegios tambien mira el subgrupo y la clave. `privilegios-ui.js` ofrece `mountEditor` (en linea), `openEditor` (ventana), `mountPrivilegesTab` y `mountTemplatesTab`; `master.html` usa la ventana. Para agregar un privilegio: entrada en `privilegios.js` + copia en functions + funcion `pXxx` y su uso en las reglas + ocultar o mostrar en la pagina + prueba en `test-emulator.mjs` (seccion "Privilegios por usuario").
- Anti-escalada tambien en las acciones: `plantillas.gestionar` cuelga de `usuarios.privilegios` (y por tanto solo admin y operador); un paraguas apagado apaga todas sus acciones aunque se las pongan en `true`. Con `usuarios.privilegios` basta para ver las plantillas del condominio; para guardarlas o borrarlas hace falta ademas `plantillas.gestionar`. El mapa de privilegios admite hasta 300 claves (un operador estrecho guarda cerca de cien en `false`).
- Orden de publicacion: reglas y functions primero (son compatibles con el front viejo: los usuarios de siempre no notan nada), el front (push a main) despues. Con el front antes que las reglas, el modal de usuario nuevo avisa de falta de permisos al leer las plantillas. Para crear `operador` y usar privilegios hacen falta las tres cosas.

## Requisitos en una PC nueva
- `node` 22 o mas, `firebase-tools`, `gcloud`, `gh` y Java 21 o mas (lo piden los emuladores).
- En Mac con Homebrew: `brew install node gh firebase-cli openjdk@21` y `brew install --cask gcloud-cli`. `openjdk@21` no queda en el PATH: agregar `$(brew --prefix openjdk@21)/bin` en `~/.zprofile`.
- En este repo, `git config user.email` con el correo noreply de GitHub (el repo es publico y el correo de cada commit queda visible).
- Entrar con una cuenta de Google con acceso al proyecto: `firebase login` y `gcloud auth login`. Para los scripts de `scripts/` tambien `gcloud auth application-default login`.
- `npm ci` dentro de `functions/` y dentro de `scripts/`.
- Si node se cuelga al importar firebase-admin, o el emulador dice "Timeout after 10000" al cargar functions: `rm -rf node_modules && npm ci` en esa carpeta.
- Puertos de emuladores: auth 9099, functions 5001, firestore 8080, hosting 5050, UI 4000.
