# CLAUDE.md - SISDEL Comunities (garita.app)

Instrucciones para cualquier sesion de Claude Code en este repo, en cualquier PC.

## Que es
Control de acceso para condominios (garita.app): paneles master, admin, vecino, garita y auditor, con camara LPR.
Multi-empresa: el rol `master` ve todo; `admin`, `policia`, `vecino`, `auditor`, `supervisor` y `operador` solo su condominio.
El `auditor` lo crea el admin: lee todo su condominio (menos los codigos de acceso), no escribe nada y tiene reportes con exportacion CSV.
Privilegios por usuario (idea de MULTISYS): el admin de cada condominio decide que puede ver o usar cada usuario. Ver la seccion "Privilegios por usuario" abajo.
Reportes (admin.html, boton Reportes): ver la seccion "Reportes y salidas" abajo.
Sistema Financiero (finanzas.html): es OIKOS, traido de MULTISYS; desde 2026-11-09 se mantiene solo aqui. Ver la seccion "Sistema Financiero" abajo.
Rondas (rondin/): es SISDEL RONDIN con su mismo diseno. Ver la seccion "Rondas" abajo.
Estructura de datos y archivos: ver README.md.

## Infraestructura
- Front: Vercel sirve garita.app directo desde la rama `main` de GitHub. Cada push a `main` publica solo.
- Backend: Firebase, proyecto `sisdel-datacenter` (Firestore, Auth, Functions en us-central1, Hosting espejo en sisdel-datacenter.web.app). Plan Blaze con la cuenta de facturacion "Garita.app" y alerta de 5 USD al mes.
- La camara envia a garita.app/api/lpr; Vercel lo reenvia a la Cloud Function `anprWebhook` (ver vercel.json). `decide.js`: un pase de visita vale lo que vale su vecino (moroso sin gracia, desactivado o eliminado: no abre ni con pase), coincidencia parcial de placas desde 6 caracteres, una visita temporal vale desde su `visitDate`; la respuesta `Close` lleva la razon real. Clave secreta por condominio en `_privado/camaras/claves/{id}` (`keyHash`; `cd scripts && npm run camera-key -- --condo=<id> --target=prod --generate|--ver|--quitar`): si existe, el webhook exige `?key=` (o `X-Camera-Key`) y responde Close "Clave de cámara inválida" sin tocar el condominio (queda en `camera_logs_huerfanos`); si no existe, la camara entra como antes. Al fijarla hay que cambiar la URL de la camara en el mismo momento. `verifyAccessCode` solo confirma vecinos (60 intentos / 10 min por usuario): confirmar el codigo de un guardia o administrador equivaldria a poder entrar con el. En `garita.html` un pase QR vale solo su dia (o su rango) y una vez, y un marbete o codigo de un vecino `active:false` no abre; el guardia resuelve alertas de panico desde la garita (`canResolve: panico.resolver`).
- El sistema anterior (Supabase) ya no se usa; sus datos se importaron el 2026-11-05.
- Acceso: GitHub `yonxela` (dueno) y `SisdelNir` (colaborador con push). Firebase: yonxela es Owner; la cuenta del papa de Yonathan es Editor + Cloud Run Admin (publica todo, no cambia permisos ni facturacion). Vercel publica los commits de cualquier colaborador porque el repo es publico.

## Privilegios por usuario
- Modelo: cada rol trae privilegios por defecto (campo `roles` de cada clave en `privilegios.js`) y son EXACTAMENTE el acceso que el rol tenia antes de este modulo. `usuarios/{id}.privilegios` guarda solo las diferencias (`{ clave: true|false }`); sin el campo, el usuario conserva el acceso de su rol (por eso no hubo migracion de datos). `usuarios/{id}.cargo` es el puesto (texto libre). El rol `operador` no trae ninguno: es el personal a la medida.
- Catalogo unico: `privilegios.js` (UMD: navegador y Node), 145 claves `modulo.accion` en grupos: 30 PARAGUAS (raices con `roles` por defecto: los 26 de siempre mas `mensajes.recibir`, `vecino.historial`, `vecino.contactos` y `reportes.ver`) y 115 ACCIONES con `parent`. Una accion no existe sin su paraguas y, con el, viene activa salvo que el usuario la tenga en `false`; hereda los roles por defecto del paraguas y su `onlyRoles`. `requires` es una dependencia blanda (la pantalla de privilegios la arrastra al marcar y quita las dependientes al desmarcar; no se comprueba en las reglas). Cada clave dice `enforce: 'reglas'` (las reglas de Firestore o el servidor la hacen cumplir) o `'pantalla'` (solo oculta en pantalla), `sensitive` y su subgrupo (`sub`). `functions/src/privilegios.js` es una COPIA IDENTICA: al cambiar uno, `cp privilegios.js functions/src/privilegios.js` (la prueba falla si difieren). Tambien trae las paginas (`PAGES`, con su privilegio de entrada), `landing()` (a donde manda el login), 11 plantillas del sistema (`TEMPLATES`, una de ellas, `sys-fiscalizador`, con rol `vecino`: un vecino con reportes en solo lectura; `SISDEL.otherPanels` ofrece `vecino.html` a un vecino con otros paneles y `vecino.html` muestra esos botones; las guardadas antes de las acciones se amplian con `expandTemplate`) y el motor de paraguas (`has`, `effective`, `toOverrides`, `toggle`, `cascade`, `childrenOf`, `descendantsOf`, `ancestorsOf`, `templateKeys`). El operador solo trae por defecto `mensajes.recibir` (leia los mensajes como miembro) y ninguna pagina.
- Las reglas leen el mapa del documento del usuario (no el token). Las funciones `pXxx(c)` NO se escriben a mano: las genera `cd scripts && npm run reglas` (entre las marcas BEGIN/END de `firestore.rules`) a partir del catalogo; un paraguas es `can(c, clave, roles)` y una accion `pParaguas(c) && childOk(c, clave)` (vale si el usuario no la tiene en `false`). Las claves `enforce: 'pantalla'` no tienen funcion (salvo los paraguas que usan sus acciones). `scripts/test-privilegios.mjs` verifica que el bloque este al dia, que cada clave y rol coincidan con el catalogo y que las funciones se usen. Las reglas ya no preguntan por el rol para dar acceso (no volver a usar `isAdmin`, `isStaff`...: usar `pXxx`). Las operaciones de Finanzas y Rondas se separan en las reglas por tipo de movimiento, campos que cambian (`diff().affectedKeys()`) y operacion (ver las secciones de abajo).
- Anti-escalada (no aflojar sin pensarlo; cada punto tiene prueba en `test-emulator.mjs`): quien crea una cuenta conoce su codigo y entra con ella, asi que `usuarios.crear` solo registra vecinos (guardias: `guardias.crear`; auditor, supervisor, admin y operador exigen ademas `usuarios.privilegios`). Nadie cambia sus propios `privilegios` ni `role` (solo el master); cambiar `privilegios` o `role`, y crear, editar o eliminar `admin` u `operador`, exige `usuarios.privilegios`; solo un `admin` u `operador` puede tener `usuarios.privilegios` (`onlyRoles` en el catalogo, `validUser` en las reglas), por eso `manageable()` puede decidir por el rol. Un codigo nuevo solo apunta a un usuario que se crea en la misma escritura (salvo `usuarios.codigos`, con el rol real del usuario y, sobre admin/operador, solo con `usuarios.privilegios`); quien ve codigos (`usuarios.codigos`) no ve ni borra los de admin/operador sin `usuarios.privilegios` (el cliente filtra `role in [vecino, policia, auditor, supervisor]`); `usuarios.eliminar` solo borra visitas, vehiculos y expedientes de un usuario que deja de existir en la misma escritura (`ownerGone`); nadie se elimina a si mismo. `usuarios.privilegios` equivale a control total del condominio: solo a administradores de confianza. Ver codigos o crear cuentas de guardia permite entrar como esa persona: tambien es sensible.
- Un solo "Salir" para todo el sistema: el boton de salida de cada pagina (`admin.html`, `garita.html`, `auditor.html`, `vecino.html`, `master.html`) pasa por `SISDEL.bindExitButton(boton, "pagina.html")`: en el panel principal del usuario (`SISDEL.homePage()`) cierra la sesion ("Salir"); en cualquier otro panel dice "Regresar al panel principal" y lleva ahi sin cerrar la sesion. No volver a usar `SISDEL.logout()` directo en el boton de una pagina.
- Salir de un modulo: en OIKOS (`finanzas.html`, funcion `exitToHome`) y en RONDIN (`rondin/js/sisdel-api.js`), "Cerrar Sesión" / "Salir" pasa a "Regresar al panel principal" (lleva a `SISDEL.homePage()` sin cerrar la sesion; OIKOS espera a que se guarde todo) cuando el modulo NO es el panel principal del usuario; si lo es (contador en OIKOS, supervisor en RONDIN) se queda "Cerrar Sesión". Se hace sin tocar `finanzas/` ni `app.js`: se relabela el boton con un MutationObserver (los menus se repintan) y el clic se intercepta en fase de captura, antes de `logout()` de OIKOS (que borraria la sesion de SISDEL). La sesion vencida de RONDIN sigue cerrandose sola con `API.logout`.
- Copiar codigos: `SISDEL.copyButton(codigo)` devuelve el boton "Copiar" (valor escapado en `data-copy`) y un escuchador global del nucleo copia el valor de cualquier `[data-copy]` con aviso; `SISDEL.copyText(texto)` hace la copia (portapapeles del navegador o respaldo con un campo oculto). Lo usan la lista de usuarios y la ventana de edicion de master.html y admin.html (en admin solo donde el usuario ya ve el codigo).
- Datos escritos por usuarios de menor confianza (nombres, telefonos, mensajes, placas y asuntos de visitas, nombre y casa de una alerta de panico) se escapan siempre al pintarlos (`esc`), tambien en `garita.html`, `panico-alertas.js` (el enlace del mapa) y en `rondin/js/sisdel-api.js` antes de pasarselos a RONDIN (que pinta con innerHTML); los ids de la base no van dentro de `onclick` (atributos `data-*` y un escuchador). Las reglas tipan `alertas_panico` (nombre, casa y telefono texto; lat/lng numero o nulo). `camera_logs.reason` se guarda SIN escapar y se escapa al pintar.
- Paginas: `SISDEL.can('clave')` muestra u oculta botones; `SISDEL.requireAuth([], 'pagina.html')` vuelve a leer la ficha del usuario (privilegios, rol y estado vigentes) y lo manda a la pagina que le toque. El login (`functions/src/auth.js`) devuelve `session.privilegios` y el destino; un usuario sin ninguna pagina no entra. Lo que se oculta en pantalla tambien lo bloquean las reglas: no confiar solo en la pagina.
- RONDIN y OIKOS se mantienen solo en este repo (desde 2026-11-09 MULTISYS queda aparte: ya no se recopian de alla y se pueden editar `rondin/js/app.js`, `rondin/css/style.css`, `rondin/js/i18n.js` y `finanzas/`). `rondin/js/sisdel-api.js` decide la pantalla por privilegios (`rondas.gestionar` = administra, `rondas.patrullar` = guardia, `rondas.ver` = solo lectura) y manda a su pagina de inicio a quien no tiene acceso. Ver "Rondas" para los privilegios por accion.
- Un solo formulario de ingreso: el de `index.html`. Ningun modulo pide su propia clave. Las paginas sin sesion mandan al login (`requireAuth`); `rondin/` tambien: `guardAccess` en `rondin/js/sisdel-api.js` redirige a `index.html?next=rondin/` y, tras entrar, el login vuelve a RONDIN si el usuario puede abrirlo (`next` solo acepta paginas de `PAGES`). Salir de RONDIN va al login (`SISDEL.logout('../index.html')`). El master va a `master.html` y el vecino a `vecino.html`, donde esta su boton de panico. La pantalla de clave original de RONDIN (`App.renderLogin`) ya no se alcanza.
- UI: `admin.html` tiene el boton "Configuracion" (encabezado) con una vista propia de tres pestanas, como el modulo de MULTISYS: Usuarios (lista con filtro por rol y Agregar Usuario, la misma de siempre), Privilegios (usuarios a la izquierda, tarjetas por modulo a la derecha, Marcar todos / Limpiar, plantillas, cambios sin guardar resaltados, Guardar / Descartar) y Plantillas (las del sistema en solo lectura; crear, editar, duplicar y borrar las del condominio en `plantillas_privilegios`). Se abre con `admin.html#configuracion/usuarios|privilegios|plantillas`. El boton lo ve quien tenga algun `usuarios.*`; con solo `usuarios.ver` todo queda en solo lectura (sin `usuarios.privilegios` no ve ni edita las plantillas del condominio). El escudo de cada usuario y Agregar Usuario siguen en el panel de siempre y abren los mismos componentes. `privilegios-ui.js` ofrece `mountEditor` (en linea), `openEditor` (ventana), `mountPrivilegesTab` y `mountTemplatesTab`; `master.html` usa la ventana. Para agregar un privilegio: entrada en `privilegios.js` + copia en functions + funcion `pXxx` y su uso en las reglas + ocultar o mostrar en la pagina + prueba en `test-emulator.mjs` (seccion "Privilegios por usuario").
- Anti-escalada tambien en las acciones: `plantillas.gestionar` cuelga de `usuarios.privilegios` (y por tanto solo admin y operador); un paraguas apagado apaga todas sus acciones aunque se las pongan en `true`. Con `usuarios.privilegios` basta para ver las plantillas del condominio; para guardarlas o borrarlas hace falta ademas `plantillas.gestionar`. El mapa de privilegios admite hasta 300 claves (un operador estrecho guarda cerca de cien en `false`).
- Orden de publicacion: reglas y functions primero (son compatibles con el front viejo: los usuarios de siempre no notan nada), el front (push a main) despues. Con el front antes que las reglas, el modal de usuario nuevo avisa de falta de permisos al leer las plantillas. Para crear `operador` y usar privilegios hacen falta las tres cosas.

## Reportes y salidas
- Boton "Reportes" en `admin.html` (junto a Configuracion, vista propia `#reportes/garita|morosos|finanzas|rondas`; el panel, Configuracion y Reportes son vistas exclusivas: `paintViews`). Todo el codigo vive en `reportes-ui.js` (`SisdelReportes.available()` y `mount()`), que se carga despues de `privilegios-ui.js`. Garita se calcula ahi con `camera_logs`, `visitas` y `salidas`; Morosos sale de los usuarios; Finanzas y Rondas son accesos directos: la contabilidad NO se recalcula fuera de OIKOS (las cifras son siempre las suyas). `finanzas.html#reportes/income|expense-cat|morosos|account-statement|resumen` abre ese reporte dentro de OIKOS (`openReportFromHash`, solo la primera vez; el privilegio lo siguen decidiendo `finanzas-bloqueo.js` y `finanzas.reportes_*`).
- Privilegios: paraguas `reportes.ver` (rol `admin`) con las acciones `reportes.garita`, `.morosos`, `.finanzas`, `.rondas` y `.exportar` (CSV e imprimir, sensible). Todas son `enforce: 'pantalla'`: los datos los protegen sus propios privilegios y reglas (garita.camara, visitas.ver, usuarios.pagos_ver, finanzas.*, rondas.panel_ver); `available()` pide ambos. La plantilla `sys-consulta` trae `reportes.ver` y `reportes.garita`; `sys-admin-sin-finanzas` no trae `reportes.finanzas`. El auditor sigue con sus reportes en `auditor.html`.
- Salidas: `garita.salida` (accion de `garita.operar`, `enforce: 'reglas'`). La salida de una visita es `visitas/{id}.exitedAt` (solo el privilegio `garita.salida` y solo si la visita ya ingreso, sin tocar otros campos; el estado sigue `entered`); `SISDEL.isVisitInside(v)` dice si esta dentro (ingreso y sin salida posterior: un acceso temporal puede volver a entrar). La salida de un vecino (marbete o codigo) es un documento de `salidas/{id}` (`kind`: `vehiculo` o `residente`; no se edita, se lee con `garita.camara`, se borra con `garita.historial_borrar`). La camara LPR solo lee entradas. En `garita.html`: boton "Registrar Salida" en la ventana de verificacion y en la lista de visitas, tarjeta "Visitas Dentro" y las salidas en el historial del dia.

## Sistema Financiero (OIKOS)
- `finanzas/` (index.html + vendor/) es OIKOS: nacio como copia de `apps/web/public/admin-finance/` de MULTISYS, pero desde 2026-11-09 se mantiene solo aqui y se edita libremente (MULTISYS queda aparte; ya no se recopia). Los cambios propios llevan comentarios `SISDEL:` (el desglose de la cuota, por ahora). Es la excepcion a la regla de emojis e iconos SVG.
- `finanzas.html` lo abre en un iframe con `?msid=<condoId>&msname=&msdirector=`; el bloque de entrada de OIKOS salta su login propio.
- `finanzas.html` entra con el privilegio `finanzas.usar` (lectura: `finanzas.ver`); ver el catalogo para las 32 acciones (tablero, residentes, cuotas y cargos, contabilidad, pagos, egresos, reportes, configuracion, deshacer, limpiar). Para registrar residentes nuevos o cambiar sus datos desde OIKOS tambien hacen falta `usuarios.crear` y `usuarios.editar` (`finanzas.residentes_crear` y `_editar` los piden como dependencia).
- Privilegios dentro de OIKOS, en tres capas (OIKOS se queda como esta: los privilegios se aplican desde fuera, sin ensuciar su codigo): (1) `firestore.rules` es la barrera real: `finanzas_residentes` separa editar, finiquitar (`status`, `closedAt`, `feeFrom`...) y eliminar (`deleted`) y admite el registro minimo `{id, feeFrom, updated_at}` y el "toque" de `updated_at`; `finanzas_movimientos` exige por tipo (`income` = pagos, `expense` = egresos, `charge` + `kind` = cuotas o cargos; las cuotas `auto: true` piden `finanzas.cuotas_mes`, las manuales cualquiera de cuota del mes, meses o cargos) y anular es un privilegio por tipo; `finanzas_config` separa cuota y cobro, datos generales y conceptos, y deja a quien opera mover `receiptCounter` y `chargedMonths`. "Deshacer" (anular o devolver una anulacion) solo alcanza lo hecho en las ultimas 2 horas (`undoWindow` en las reglas y `UNDO_WINDOW_MS` en el cliente). (2) `finanzas-sync.js` filtra cada subida (`gate` antes de `push`, con `movementNeeds`, `residentNeeds` y `settingsNeeds`, espejo de las reglas): descarta lo que el usuario no puede escribir y restaura la copia local desde la nube; si OIKOS genera cuotas automaticas al abrir y el usuario no puede cobrarlas, se descartan en silencio. (3) `finanzas-bloqueo.js` (cargado por `finanzas.html` en cada `load` del iframe, que queda oculto hasta aplicarlo) oculta menus y botones con una hoja de estilos, bloquea clics, envios y Ctrl+Z en fase de captura segun el atributo `onclick`/`onsubmit`, redirige a la primera pantalla permitida y envuelve `deleteTransaction` (privilegio por tipo), `checkMonthlyFees`, `saveSettings` y `History.undo/redo`. Es solo de pantalla: el iframe es del mismo origen y se puede saltar desde la consola; por eso ver el tablero, el DPI, los reportes y su exportacion son `enforce: 'pantalla'` (las reglas dejan leer todo a quien tiene `finanzas.ver`).
- `finanzas-sync.js` conecta el localStorage de OIKOS con Firestore. Una sola base de vecinos: los residentes de OIKOS son los vecinos de SISDEL (nombre, casa y telefono en `usuarios`); DPI, lote, notas y finiquito en `finanzas_residentes/{mismo id}`, que solo leen admin, auditor y master. Movimientos en `finanzas_movimientos`, configuracion en `finanzas_config/oikos_settings`.
- Nada se borra (OIKOS anula con `deleted: true`). Cada vecino se cobra desde el mes en que entra al sistema (`feeFrom`), y un condominio nuevo arranca en quetzales y cobro manual.
- Los residentes se ingresan en OIKOS: cada residente nuevo se crea como vecino de SISDEL con su codigo. Las placas se siguen registrando en el panel admin.
- Mora automatica (`functions/src/finanzas/`): se activa sola con el primer cargo del condominio (`condominios/{id}.moraAutomatica`). Desde ahi `paymentStatus` y `morosoSince` los escribe solo el servidor (las reglas no dejan al admin cambiarlos) y el panel admin muestra "Calculado por el Sistema Financiero".
  - Moroso para la garita = debe MAS de una cuota vencida (OIKOS muestra mora desde la primera). La cuota del mes vence pasado el dia de cobro + dias de gracia de OIKOS; la camara aplica despues la gracia del condominio (reminderEnabled/gracePeriodDays).
  - Se recalcula al registrar o anular un cargo o pago (`onFinanceMovement`), al cambiar cuota/dia/gracia/modo (`onFinanceSettings`) y cada dia a las 05:00 de Guatemala (`dailyFinance`, que tambien crea las cuotas del mes en modo automatico, con el mismo id que OIKOS: fee_<vecino>_<AAAA-MM>).
  - `mora.js` replica funciones de OIKOS (cuotas, mora y, con el desglose, la descripcion de la cuota): si cambia una, revisar que la otra siga igual.

- Revision de dinero (2026-11-09), lo que OIKOS hace distinto a MULTISYS (todo con comentario `SISDEL:` en `finanzas/index.html`): `History` guarda fotos CRUDAS (con anulados) y se vacia en el evento `storage` cuando `finanzas-sync.js` escribe un cambio de otro equipo o del servidor (antes deshacer reescribia la lista sin ese movimiento y la sincronizacion lo subia como anulado); `getNextReceiptNumber` parte del mayor numero ya emitido y salta los repetidos; `localDayKey(iso)` es el dia local y lo usan todos los filtros por fecha y agrupaciones por mes; `handleTransactionSubmit` exige monto > 0 y residente antes de numerar o de guardar la foto para deshacer; `defaultSettings.fee` es 0 y `saveSettings` guarda la suma del desglose (0 = no se cobra), `chargeDay` numero 1-28 y `graceDays` 0 vale 0; el formulario muerto "Cargar Saldo Inicial" se quito (registraba la deuda como egreso de caja); `buildMorososReport` parte del saldo real y reparte pagos sobre todos los cargos vivos; `getEcData` arranca con el saldo anterior al rango; el tablero no cuenta finiquitados como morosos; `checkIsMoroso` tolera dia de cobro + gracia que pase de fin de mes.
- `finanzas-sync.js` sube SOLO los campos que cambiaron (`changedFields` + `set(..., { merge: true })`) en residentes, movimientos y configuracion, para no pisar con una copia vieja un finiquito, una anulacion o la cuota que otro equipo cambio mientras tanto; el registro minimo de un vecino (`saveExtras`, y `recalc.js`) tambien va con merge; si una subida falla, `synced` vuelve a lo anterior (el reintento se evalua como el mismo cambio, no como un alta); `residentNeeds` exige ademas `usuarios.crear` (residente nuevo) y `usuarios.editar` (nombre, casa, telefono); y `sisdel_fin_conocidos_<condo>` recuerda los vecinos que este equipo ya vio en la nube para no recrear (con codigo nuevo) uno que el administrador elimino, aunque quedara en una copia local pendiente (`dropResurrected`). Un vecino con `finanzas_residentes.deleted` vuelve a `al_dia` en el servidor (`recalc.js`). Las reglas exigen `amount is number && amount > 0` al crear movimientos. Limite conocido: la mezcla sigue decidiendose por el reloj de cada equipo (`updated_at`).
- Desglose de la cuota mensual: la cuota es la suma de hasta cinco conceptos (mantenimiento, agua, recoleccion de basura, electricidad y otros) que se escriben en Configuracion de OIKOS (`settings.feeBreakdown`; `settings.fee` sigue siendo la suma, solo lectura en pantalla). Al cobrar la cuota (automatica, "Cuota del mes", meses de un residente o servidor) el movimiento sigue siendo UNA linea y su concepto nombra solo los conceptos con monto, p. ej. "Por aporte para mantenimiento y servicio de agua Q 500.00" (mantenimiento 400 + agua 100); guarda ademas `breakdown` ({ maintenance: 400, water: 100 }) y `period` sigue siendo la llave de la cuota. Sin desglose configurado, o si el cobro es de otro monto que la suma, el concepto sigue siendo "Cuota - Mes Año". La logica vive en `finanzas/sisdel-cuotas.js` (UMD; OIKOS la carga y `functions/src/finanzas/cuotas.js` es una COPIA IDENTICA que usa `mora.js` para las cuotas del dia: al cambiar uno, copiarlo al otro; la prueba `test-finanzas-cuotas.mjs` falla si difieren). `feeBreakdown` es un privilegio de la cuota (`finanzas.config_cuota`) en las reglas, en `finanzas-sync.js` y en el bloqueo de pantalla (los cinco campos se deshabilitan). Las cuotas ya cobradas conservan su descripcion. Un condominio que ya tenia cuota y abre Configuracion ve su cuota completa en Mantenimiento; la descripcion nueva empieza al guardar.

## Rondas: SISDEL RONDIN (rondin/)
- Es el programa RONDIN con su mismo diseno y opciones: `rondin/index.html`, `rondin/css/style.css`, `rondin/js/app.js` e `i18n.js` nacieron como copias de `RONDIN/public` y desde 2026-11-09 se mantienen solo aqui (si se edita `app.js`, revisar que sus llamadas `/api/...` sigan existiendo en el adaptador). Es la excepcion a la regla de emojis e iconos SVG. Las pipas quedaron fuera; Rondin Air (drones) esta incluido.
- Privilegios de RONDIN por accion (`rondas.*`): `rondin/js/privilegios-rondin.js` (UMD, se prueba en `scripts/test-rondas-privilegios.mjs`) tiene la tabla de rutas `/api/...` y el privilegio que exige cada una (`route()` de `sisdel-api.js` devuelve 403 si falta; una prueba exige que TODA ruta registrada en el adaptador este en la tabla o en la lista de rutas abiertas), las pantallas del menu (`App.navigate` con lista blanca; las pantallas huerfanas nunca se abren), la hoja de estilos que oculta botones por `onclick` y los metodos de `App` envueltos. `startRealtime` abre cada escucha solo con el privilegio de lo que escucha, `dispatchDrone` exige `rondas.drones_operar`, el tablero (`dgData`) tolera lecturas sin permiso y el expediente del guardia (`rondas.guardias_expediente`) se corta en `userOut`. Las reglas separan rutas (crear, desactivar), puntos (agregar, quitar o renombrar se distinguen por el cambio en la cantidad de `checkpoints`), asignaciones, alertas, incidentes, drones, configuracion, supervisor asignado y la patrulla (iniciar, marcar, terminar, rastrear); ver el mapa en vivo y el historial de ubicaciones son privilegios sensibles. El panel, los reportes, las listas de guardias y supervisores y el expediente son `enforce: 'pantalla'`.
- `rondin/js/sisdel-api.js` reemplaza al servidor de RONDIN (Express + SQLite en Render): define `API`, un `io()` sobre Firestore (tiempo real) y atiende los `fetch('/api/...')`. Responde las mismas rutas con los datos de SISDEL.
- Una sola base: empresa = condominio; guardias = `policia`, supervisores = `supervisor`, director general = `admin` (el `auditor` ve lo mismo en solo lectura; con privilegios a la medida, un `operador` puede ser cualquiera de ellos: ver "Privilegios por usuario"); el PIN de RONDIN es el codigo de acceso de SISDEL. Vecinos = los de SISDEL: DPI en `finanzas_residentes.dpi` (el del Sistema Financiero), familiares en `emergencia/{userId}`. Un vecino creado en RONDIN entra al Sistema Financiero desde ese mes (`feeFrom`).
- Datos propios con el formato de RONDIN (`company_id`, `guard_id`, fechas `AAAA-MM-DD HH:MM:SS` en UTC): `rondas_rutas` (con sus puntos), `rondas_asignaciones`, `rondas_turnos`, `rondas_rondas`, `rondas_visitas`, `rondas_ubicaciones`, `rondas_en_vivo`, `rondas_incidentes`, `rondas_alertas` (panel de alertas), `rondas_fotos`, `rondas_personal` (expediente del guardia), `rondas_config/general`, `rondas_drones`.
- El supervisor registra guardias (solo `policia`) y ve sus codigos; no ve los de los demas. `rondas.html` y `rondin.html` solo redirigen a `rondin/`.
- Boton de panico: guardias (RONDIN) y vecinos (RONDIN o vecino.html) crean `alertas_panico`. En vecino.html el boton aparece solo si RONDIN > Configuracion > "Vecinos usaran boton de panico" esta activo. `panico-alertas.js` (con `rondas-core.js`, que quedo solo para panico y contactos) los muestra en garita y admin; RONDIN tiene su propia alarma. `onPanicCreated` avisa por WhatsApp a la central, al admin y supervisores y a los familiares del vecino (hasta 5).
- WhatsApp: UltraMsg (principal) y Meta (respaldo), claves en `_privado/whatsapp`. Las carga una persona con `cd scripts && GOOGLE_CLOUD_QUOTA_PROJECT=sisdel-datacenter node set-whatsapp.mjs --target=prod` (sin claves, la alerta queda registrada como "WhatsApp sin configurar"). Con `--probar` verifica las claves con el proveedor sin enviar mensajes; con `--ver` muestra que esta configurado. En el emulador el proveedor es "simulado".
- `dailyRondas` (03:00 de Guatemala) cierra turnos de mas de 16 h y rondas de mas de 6 h (con su puntaje: % de puntos obligatorios, completa desde 80 %, igual que RONDIN) y borra posiciones de mas de 30 dias y alertas del panel de mas de 90.

## Requisitos en una PC nueva
- `node` 22 o mas, `firebase-tools`, `gcloud`, `gh` y Java 21 o mas (lo piden los emuladores).
- En Mac con Homebrew: `brew install node gh firebase-cli openjdk@21` y `brew install --cask gcloud-cli`. `openjdk@21` no queda en el PATH: agregar `$(brew --prefix openjdk@21)/bin` en `~/.zprofile`.
- En este repo, `git config user.email` con el correo noreply de GitHub (el repo es publico y el correo de cada commit queda visible).
- Entrar con una cuenta de Google con acceso al proyecto: `firebase login` y `gcloud auth login`. Para los scripts de `scripts/` tambien `gcloud auth application-default login`.
- `npm ci` dentro de `functions/` y dentro de `scripts/`.
- Si node se cuelga al importar firebase-admin, o el emulador dice "Timeout after 10000" al cargar functions: `rm -rf node_modules && npm ci` en esa carpeta.
- Puertos de emuladores: auth 9099, functions 5001, firestore 8080, hosting 5050, UI 4000.

## Herramientas y diagnostico
- `scripts/set-master-code.mjs --target=prod --generate` (con `GOOGLE_CLOUD_QUOTA_PROJECT=sisdel-datacenter`): genera un codigo master nuevo, guarda solo su hash en `_privado/auth`, cierra las sesiones master abiertas y muestra el codigo una sola vez. Lo corre una persona en su terminal: el modo automatico de Claude no deja escribir credenciales en produccion.
- `scripts/set-camera-key.mjs` (`npm run camera-key -- --condo=<id> --target=prod --generate`): clave secreta de la camara de un condominio (ver Infraestructura). Lo corre una persona; la clave se muestra una vez.
- `scripts/migrate-supabase.mjs`: importacion del sistema anterior (ya hecha).
- `cd scripts && npm run reglas` regenera las funciones `pXxx` de `firestore.rules` desde `privilegios.js` (`--check` solo verifica); `node scripts/generar-tabla-privilegios.mjs` regenera la tabla de privilegios del README (`--check` la verifica). Las dos las verifica `npm test`.
- Coleccion `_diag`: cada pagina guarda cuanto tardo en cargar (login, sesion, datos, red, navegador). Solo el master la lee; se consulta con el admin SDK desde `scripts/` para diagnosticar lentitud.
- Bitacora de logins en Cloud Logging: servicio `login`, campo `jsonPayload.outcome` (ok, not_found, blocked, condo_inactive, user_inactive).
